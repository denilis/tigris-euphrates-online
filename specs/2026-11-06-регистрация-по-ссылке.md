# Регистрация по ссылке-приглашению (одобрено Денисом 06.11, «Да, обе ссылки»)

## Проблема
Новичок без кода не может играть: код ему заводит другой игрок в «Кодах игроков», вписывая имя
за него, потом код пересылается отдельно. Позвать знакомого «по ссылке на игру» нельзя.

## Цель
Любой игрок дает ссылку, новичок по ней сам вписывает имя или ник, получает код и сразу входит.
Ссылка за стол еще и сажает его на свободное место.

## Критерии приемки
1. В «Кодах игроков» у любого игрока кнопка «Создать ссылку-приглашение»: ссылка на одного
   человека, действует 7 дней, показывается один раз с кнопкой «Скопировать».
2. Там же список действующих ссылок (когда создана, до какого числа, за какой стол) с «Отозвать».
3. В лобби кнопка «Ссылка для нового игрока»: та же ссылка, но за этот стол. Пока партия не началась.
4. По ссылке без кода: экран «X приглашает вас (за стол Y)», поле «Как вас будут видеть другие
   игроки» (имя или ник, 1-30 знаков, без почты и телефона), «Получить код и войти».
5. После регистрации: код показан один раз с «Скопировать», человек уже вошел; ссылка за стол ведет
   на стол и сажает на первое свободное место.
6. Новичок в списке пригласившего (invitedBy), как при выдаче кода вручную.
7. Использованная, отозванная, просроченная ссылка или ссылка от отозванного игрока: понятное
   «ссылка уже не действует, попросите новую». Занятое имя: «такое имя уже есть», ссылка не сгорает.
8. Уже вошедший человек по чужой ссылке не регистрируется второй раз: «вы уже вошли как X».
9. Экран входа: вместо «код выдает администратор» сказано, что код дает пригласивший игрок.

## Ограничения
- Ссылка хранится отпечатком (HMAC с солью, как коды): утечка базы не дает рабочих ссылок.
- Токен ссылки в адресе после # (до сервера и в журналы Vercel не доходит), на API уходит телом POST.
- Подбор ссылок: 128 бит случайности плюс лимит попыток с адреса, как у входа по коду.
- У любого игрока, и у администратора тоже, не больше 10 действующих ссылок сразу. Не администратор
  вдобавок заводит не больше 10 новых игроков в сутки (общий счетчик с ручной выдачей кода).
- Список ссылок игрока хранится хешем Redis, поле на ссылку: одновременные создание, регистрация и
  просмотр списка друг друга не затирают (ревью 06.11).
- Отзыв кода игрока гасит все его ссылки насовсем: новый код их не возвращает.
- Имя чистится: NFKC, без невидимых знаков, пробелы одиночные; двойник с невидимым знаком не пройдет.
- Одна ссылка = один человек: забор ссылки атомарный (GETDEL), два новичка одну ссылку не используют.

## Не делаем
- Общая ссылка на группу людей (утечет, и зарегистрируются чужие).
- Почта, телефон, восстановление кода (код заново выдает пригласивший, как сейчас).
- Открытая регистрация без приглашения (персональные данные, см. разговор 06.11).

## План
1. auth.js: newJoinToken, joinHash, isJoinToken.
2. Хранилище (память, Redis, поддельный Upstash): putJoin / getJoin / takeJoin (GETDEL) / dropJoin,
   getJoinList / setJoinList (список ссылок игрока).
3. routes.js: POST join/info {token} и POST join {token, name} без входа; joinlinks: GET (свои
   действующие), POST {table?} (создать), POST joinlinks/<id>/revoke.
4. Клиент: public/js/join.js (страница новичка, ссылка), маршрут #/join/<токен> до проверки входа,
   «Коды игроков» (кнопка, ссылка один раз, список с отзывом), лобби (кнопка за стол),
   presence.markAccepted для посадки, текст экрана входа.
5. Тесты: test/join.test.js (API целиком, в памяти и на поддельном Upstash), хранилище.

## Разбор вариантов
- Посадка на сервере в момент регистрации: надежнее при гонке за место, но тянет логику стола в
  регистрацию. Выбрано: посадка тем же путем, что приглашение «С людьми» (клиент садится сам,
  сервер проверяет место); если мест нет, человек видит лобби и сообщение.
- Многоразовая ссылка: удобна для чата, но опасна. Выбрано: на одного человека.
- Хранить токен открыто, чтобы ссылку можно было скопировать позже: удобно, но утечка базы дает
  рабочие ссылки. Выбрано: отпечаток, ссылка показывается один раз, как код.
