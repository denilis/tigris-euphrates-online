# Tigris & Euphrates — Online

Онлайн-версия настольной игры Райнера Книции «Тигр и Евфрат» для 2–4 игроков. Правила игры применяет движок: царства, конфликты, очки, сокровища, монументы и конец игры считаются автоматически, по официальному своду правил Fantasy Flight Games (стандартная сторона поля, базовая игра).

## Режимы

- **Онлайн.** Один игрок создаёт комнату и отправляет код или ссылку-приглашение, остальные входят по ним. Партию ведёт сервер: у каждого игрока своя рука и свои очки, соперники их не видят.
  - После перезагрузки страницы или обрыва связи игрок возвращается на своё место автоматически.
  - Если игрок, от которого ждут хода или решения, не выходит на связь дольше 75 секунд, остальные могут пропустить его: ход заканчивается, в конфликте он не добавляет тайлов. «Не в сети» показывается через 40 секунд тишины.
- **На одном устройстве.** Игроки передают устройство друг другу, перед каждым ходом показывается закрывающий экран. Если в конфликте решает не активный игрок, экран передачи тоже появляется. Партия сохраняется в браузере после каждого действия.
  - Режим «тренировка» убирает экран передачи — удобно, чтобы разобраться в правилах в одиночку.

## Что реализовано из правил

- Поле 16×11 — раскладка официального стандартного поля: 41 речная клетка и 10 стартовых храмов с сокровищами (картинка `field.png` показывает это поле повёрнутым на 180°, координаты приведены к ней). В мешке 143 тайла (47 храмов, 36 ферм, 30 рынков, 30 поселений). У каждого игрока династия из четырёх лидеров, две катастрофы и 6 тайлов в руке.
- Два действия за ход:
  - лидер: поставить, переместить или убрать;
  - тайл;
  - катастрофа;
  - обмен до 6 тайлов (сброшенные уходят из игры).
- Ход можно закончить раньше.
- Ограничения на размещение:
  - фермы кладутся только на реку, остальные тайлы — только на сушу;
  - лидер ставится только рядом с храмом и не может объединять царства;
  - тайл не может объединить больше двух царств.
- Очки за тайл получает лидер того же цвета, а если его нет — царь. Тайл, объединивший два царства, очков не даёт.
- **Восстания.** Сила — храмы рядом с лидером плюс храмы из руки. Первым добавляет атакующий. При ничьей побеждает защитник. Победитель получает красное очко.
- **Войны:**
  - порядок войн выбирает активный игрок;
  - атакующий определяется по часовой стрелке от активного игрока;
  - сила — сторонники в своей части царства плюс тайлы из руки;
  - проигравший теряет сторонников, кроме храмов с сокровищами и храмов рядом с другими лидерами;
  - после каждой войны царство пересчитывается, и следующая война может не начаться.
- **Катастрофы:** нельзя класть на лидера, сокровище или монумент. Лидер, у которого не осталось соседнего храма, уходит с поля.
- **Монументы:** возводятся на квадрате 2×2 из тайлов одного цвета. В конце своего хода игрок получает очки за своих лидеров цвета монумента в том же царстве.
- **Сокровища:** торговец царства, где их два или больше, забирает все, кроме одного. Сначала — сокровища четырёх храмов с особой рамкой у краёв поля (на поле они обведены золотом), остальные — на выбор.
- **Конец игры:** в конце хода на поле осталось не больше двух сокровищ, или из мешка нечего добрать. Итог считается по самой слабой сфере, сокровища игрок распределяет сам. При равенстве сравниваются следующие сферы.

Не реализованы продвинутые варианты из свода правил: здания цивилизации, «чудо», продвинутая сторона поля и «английский» вариант подкрепления.

## Как устроено

```
Браузер ──HTTPS──▶ Vercel: статика public/ + функции api/ (регион fra1)
   ▲                  │ секретный ключ, PostgREST
   │                  ▼
   │           Supabase Postgres (eu-central-1): te_rooms, te_presence, функции te_*
   │                  │
   └──WebSocket── Supabase Realtime ◀── функция после каждого хода шлёт «комната изменилась, rev N»
```

- **Партия хранится в Postgres** одной строкой `te_rooms` (JSON комнаты и состояния движка) с номером ревизии `rev`. Каждое изменение — «прочитать → применить правило → сохранить, если `rev` не изменился», иначе повтор. Поэтому любое число экземпляров функций может одновременно обслуживать одну партию, а двойной клик не применит ход дважды.
- **Браузер не видит базу.** Таблицы закрыты RLS без политик, у ролей `anon`/`authenticated` нет прав ни на таблицы, ни на функции. Функции Vercel работают с секретным ключом. Каждый игрок получает только свой вид партии.
- **Обновления.** После хода функция отправляет в канал Supabase Realtime `te:<код>` только номер ревизии, без содержимого партии. Страницы соперников сразу запрашивают свой вид. Пока подписка работает, страница опрашивает сервер раз в 15 секунд — это ещё и сигнал «я в сети». Если Realtime недоступен (не задан публичный ключ, сеть блокирует `supabase.co`, локальный запуск), страница опрашивает сервер каждые 2,5 секунды: игра работает, только медленнее и дороже по числу запросов.
- **Почему не WebSocket-сервер на Vercel.** Он в статусе бета. Соединение рвётся по лимиту длительности функции, переподключение попадает на другой экземпляр, а открытое соединение тарифицируется как работающая функция. Поэтому состояние всё равно пришлось бы хранить снаружи.

## Деплой: Vercel + Supabase

### 1. Supabase

1. Создайте проект в [дашборде Supabase](https://supabase.com/dashboard). Регион — **Central EU (Frankfurt), `eu-central-1`**: функции Vercel настроены на соседний `fra1`, в `vercel.json` → `regions`. Если выберете другой регион Supabase, поменяйте и `regions` на ближайший регион Vercel.
2. **SQL Editor** → вставьте и выполните [`supabase/migrations/20260926075126_te_rooms.sql`](supabase/migrations/20260926075126_te_rooms.sql). Повторный запуск безопасен. Вместо этого можно выполнить `supabase db push` из Supabase CLI.
3. **Project Settings → API Keys**: вам понадобятся Project URL, **publishable key** (`sb_publishable_…`) и **secret key** (`sb_secret_…`). Секретный ключ никогда не должен попадать в браузер или в репозиторий.

### 2. Vercel

1. **Add New → Project** → импортируйте репозиторий из GitHub. Framework Preset определяется из `vercel.json` («Other»), сборка — `npm run build`, раздаётся папка `public/`.
2. **Settings → Environment Variables** (для Production и Preview):

   | Переменная | Значение | Обязательна |
   |---|---|---|
   | `SUPABASE_URL` | `https://<ref>.supabase.co` | да |
   | `SUPABASE_SECRET_KEY` | `sb_secret_…` (или старый `service_role`) | да |
   | `SUPABASE_PUBLISHABLE_KEY` | `sb_publishable_…` (или старый `anon`) | для мгновенных обновлений через Realtime; без неё страницы опрашивают сервер |
   | `CRON_SECRET` | любая длинная случайная строка | рекомендуется: без неё `/api/cron` может вызвать кто угодно (вреда нет, чистятся только брошенные комнаты) |

   Подойдут и имена, которые синхронизирует интеграция Supabase из Vercel Marketplace: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ANON_KEY`.
3. **Deploy** (после изменения переменных — **Redeploy**: новые значения действуют только для новых деплоев).
4. Проверка: откройте `https://<домен>/api/health`. Ожидается `{"ok":true,"store":"supabase","realtime":true,…}`. `503` с текстом ошибки означает, что не заданы переменные или не применена миграция.

Прочее:

- **Кому давать ссылку.** Давайте адрес production-деплоя. Preview-деплои (ветки и PR) у новых проектов обычно закрыты Vercel Authentication (Standard Protection) и без входа в Vercel не откроются: Settings → Deployment Protection.
- **Cron** (`vercel.json` → `crons`) раз в сутки удаляет брошенные комнаты: лобби без изменений 6 часов, законченные партии через 2 дня, любые — через 14 дней. Второй запуск раз в сутки проверяет `/api/health`. Оба запроса заодно создают активность в базе. Cron работает только на production-деплое.

### Лимиты бесплатных тарифов

Оценка на одну партию вчетвером длиной около часа при работающем Realtime. Число ходов взято из замера: 150 случайных партий движка, в среднем около 165 действий.

| Что | Расчёт | На партию |
|---|---|---|
| Вызовы функций | 4 игрока × 240 heartbeat/ч + ~170 ходов + ~510 запросов соперников после ходов (3 × 170) | ≈ 1 650 |
| Сообщения Realtime | ~170 изменений × (1 отправка + 4 получателя) | ≤ 850 |
| Исходящий трафик Supabase | до ~680 чтений партии × ~15–21 КБ, если кэш функции промахнулся (обычно меньше) | ≤ 15 МБ |

- **Vercel Hobby** даёт 1 000 000 вызовов в месяц. Это около 600 таких партий-часов. Без Realtime (опрос каждые 2,5 с) — около 170. Процессорного времени (4 CPU-часа) хватает с запасом: логика игры занимает доли миллисекунды CPU на запрос. **Hobby разрешён только для некоммерческого использования.** При превышении лимитов функции останавливаются до конца 30-дневного периода.
- **Supabase Free** даёт 5 ГБ egress и 2 млн сообщений Realtime в месяц на организацию, базу 500 МБ и 200 одновременных подключений Realtime. Бесплатный проект **ставится на паузу после недели низкой активности**, и снять её можно только в дашборде. Cron добавляет два запроса в сутки, но Supabase не гарантирует, что этого достаточно. Надёжные варианты — тариф Pro или внешний монитор (например, UptimeRobot), который раз в несколько часов открывает `/api/health`.

## Локальный запуск

Нужен Node.js 22 или новее: этого требует `@supabase/supabase-js`.

```bash
npm install
npm start        # http://localhost:3000
npm test         # движок, API, HTTP; тест базы — если заданы TEST_SUPABASE_*
```

- **Без переменных Supabase** комнаты хранятся в памяти процесса. Для игры по локальной сети или разработки этого достаточно, но перезапуск сервера обрывает партии. Так же сервер можно запустить на любом Node.js-хостинге (`Procfile` есть), но только в одном экземпляре.
- **С переменными** (`SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_PUBLISHABLE_KEY`) локальный сервер работает с той же базой и Realtime, что и деплой.
- `TEST_SUPABASE_URL`, `TEST_SUPABASE_SECRET_KEY` и необязательный `TEST_SUPABASE_PUBLISHABLE_KEY` включают интеграционный тест `test/supabase.test.js`. Цель — проект Supabase, `supabase start` или PostgREST с применённой миграцией. Тест удаляет за собой созданные комнаты.

## Структура

```
api/                      функции Vercel: game (все запросы игры), config, health, cron
lib/rooms.js              правила комнаты: места, лобби, старт, ходы, пропуск, реванш (чистые функции)
lib/api.js                API: операции, ревизии и повторы при гонках, кэш комнат в экземпляре
lib/store/supabase.js     хранилище на Supabase (функции te_*) и уведомления Realtime
lib/store/memory.js       то же в памяти процесса — для локального запуска и тестов
lib/http.js, runtime.js   обработчики (req, res) и сборка API из переменных окружения
dev-server.js             локальный сервер: те же обработчики + статика
supabase/migrations/      схема базы: таблицы, RLS, функции te_*
shared/engine.js          движок правил (общий для сервера и браузера, без зависимостей)
public/                   страница: index.html, css/, js/app.js, assets/
scripts/build.js          сборка для Vercel: кладёт engine.js и supabase-js в public/
assets-src/               исходные фото фишек, тайлов и поля (в игру напрямую не отдаются)
tools/prepare-assets.py   сборка public/assets/game из assets-src (нужен Pillow)
test/                     node:test — движок (сценарии и 150 случайных партий), API, HTTP, база
```

Движок детерминирован и не изменяет переданное состояние: `applyAction(state, player, action)` возвращает новое состояние или ошибку. Поэтому некорректный или враждебный запрос не может испортить партию или уронить сервер.

### API

`POST /api/game` с JSON `{ op, … }`. Ответ — `{ ok: true, … }` или `{ ok: false, error, gone?, stale? }`:

- `gone` — комнаты или места больше нет, страница забывает сессию;
- `stale` — ход сделан по устаревшему экрану, страница перечитывает партию.

Успешные ответы несут снимок `{ rev, room, view, now, onlineMs, skipAfterMs }`, где `view` — только то, что этот игрок имеет право видеть.

- **Комната:**
  - `create { name, maxPlayers }` → `code`, `token`;
  - `join { code, name }` → `code`, `token`;
  - `sync { code, token, since }` — если `since` равен текущей ревизии, приходит `unchanged: true` без `view`;
  - `dynasty { …, dynasty }`;
  - `start`;
  - `leave`.
- **Партия:**
  - `action { code, token, rev, action: { type, … } }` — `tile`, `leader`, `withdraw`, `catastrophe`, `swap`, `end`, `commit`, `war`, `monument`, `treasure`;
  - `skip { …, rev }`;
  - `rematch { …, rev }`.

Лимиты: тело запроса до 16 КБ, не больше 10 новых комнат за 10 минут с одного адреса.
